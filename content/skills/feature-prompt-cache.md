**캐시가 안 먹는 이유의 90%는 시스템 프롬프트 어딘가에 들어간 현재 시각입니다.**

## 왜 알아야 하나

같은 문서나 긴 지시문을 여러 요청에서 반복해 보낸다면, 매번 전액을 내고 있는 셈입니다. 캐싱은 그 반복 구간을 약 0.1배 비용으로 읽게 해줍니다.

문제는 **조용히 실패한다**는 점입니다. 오류가 나지 않고 그냥 캐시가 안 먹습니다. 그래서 원리를 알고 설계해야 합니다.

## 개념 잡기

캐싱은 **접두사 일치**입니다. 프롬프트 앞에서부터 바이트가 같은 구간까지만 재사용되고, 한 글자라도 달라지면 그 뒤는 전부 다시 계산합니다.

렌더 순서는 `tools` → `system` → `messages`. 따라서 설계 원칙은 하나입니다.

**안정적인 내용을 앞에, 매번 바뀌는 내용을 뒤에.**
캐시를 조용히 깨뜨리는 것들:

| 패턴 | 왜 문제인가 |
|---|---|
| 시스템 프롬프트의 현재 시각·UUID | 매 요청 앞부분이 달라짐 |
| 정렬하지 않은 JSON 직렬화 | 키 순서가 흔들림 |
| 사용자마다 다른 도구 목록 | 도구는 맨 앞이라 전부 무효화 |
| 조건부 시스템 섹션 | 조합마다 다른 접두사 |

## 바로 해보기

1. 같은 앞부분으로 두 번 요청하고 응답의 `cache_read_input_tokens`를 확인합니다.
2. 값이 계속 0이라면, 두 요청의 프롬프트를 파일로 저장해 **바이트 단위로 diff**합니다.
3. 차이가 나는 부분을 프롬프트 뒤쪽으로 옮깁니다.
4. 다시 측정해 캐시 읽기가 잡히는지 확인합니다.

## 흔한 실수

- **❌ 캐시 마커만 붙이고 순서는 그대로 둔다** — 마커보다 순서가 중요합니다. 앞쪽에 변동 요소가 있으면 마커를 붙여도 소용없습니다.
- **❌ 시스템 프롬프트에 사용자 이름·세션 ID를 넣는다** — 사용자마다 다른 접두사가 되어 공유가 불가능해집니다. 이런 값은 메시지 쪽으로 옮기세요.
- **❌ 매 요청 내용이 다른데도 캐싱을 켠다** — 재사용이 없으면 쓰기 비용(약 1.25배)만 냅니다. 이 경우엔 끄는 게 이득입니다.

## 스스로 점검하기

**Q1. 캐시 적중 여부는 어디서 확인하나요?**

정답: 응답 usage의 `cache_read_input_tokens`입니다. 반복 호출에도 0이면 무효화 요인이 있는 것입니다.

**Q2. 몇 번 재사용해야 이득인가요?**

정답: 5분 TTL 기준 두 번만 재사용해도 이득입니다.
