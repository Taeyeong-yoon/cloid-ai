> 매번 뜨는 승인 창을 사람이 정말 읽고 있었는가 — 이 질문에서 출발한 변화입니다.

## 왜 알아야 하나

Claude Code는 파일을 고치거나 명령을 실행할 때마다 멈춰 승인을 물었습니다. 안전해 보이지만 함정이 있습니다. **창이 반복될수록 사람은 읽지 않고 누릅니다.** 확인 절차가 형식만 남는 것이죠.

2026년 8월부터 유료 사용자 기본값이 된 Auto Mode는 그 프롬프트를 없애는 대신 **백그라운드 안전 검사**를 붙였습니다. 사람의 형식적 승인보다 자동 검사가 낫다는 판단입니다.

이 변화 때문에 "내가 지금 어떤 모드로 일하고 있는지" 아는 것이 전보다 중요해졌습니다.

## 개념 잡기

| 모드 | 승인 없이 실행되는 것 | 적합한 상황 |
|---|---|---|
| `default` | 읽기만 | 처음 쓸 때, 민감한 작업 |
| `acceptEdits` | 읽기 + 파일 수정 + 기본 파일 명령 | 내가 보면서 반복 수정할 때 |
| `plan` | 읽기 (+ 검사 통과 명령) | 바꾸기 전에 구조부터 볼 때 |
| `auto` | 전부, 백그라운드 안전 검사 동반 | 긴 작업, 승인 피로가 클 때 |
| `dontAsk` | 미리 허용한 도구만 | 허용 목록을 직접 관리할 때 |
| `bypassPermissions` | 전부, 검사 없음 | 격리된 환경에서만 |

핵심은 위에서 아래로 갈수록 **자율성이 올라가고 통제가 내려간다**는 것입니다. 하나를 골라 고정하는 게 아니라, 작업 단계마다 옮겨 다니는 것이 정상적인 사용법입니다.

## 바로 해보기

1. 세션에서 `Shift+Tab`을 눌러 모드를 순환시키고, 상태 표시줄 표시가 어떻게 바뀌는지 확인합니다.
2. `plan` 모드에서 "이 프로젝트 구조를 설명해줘"를 실행합니다. 읽기만 하므로 안전합니다.
3. `acceptEdits`로 바꿔 작은 수정을 맡기고, 승인 창이 줄어드는 체감을 확인합니다.
4. 마지막으로 내 작업 목록을 보고, 각 작업에 어떤 모드가 맞을지 한 줄씩 적어 봅니다.

## 흔한 실수

**❌ 편하다는 이유로 `bypassPermissions`를 상시로 켜둔다**

→ `bypassPermissions`는 안전 검사까지 끄는 모드입니다. 자율성이 필요하면 `auto`를 쓰세요 — 검사는 유지됩니다.

**❌ 한 모드를 정해두고 계속 쓴다**

→ 탐색은 `plan`, 수정은 `acceptEdits`, 긴 작업은 `auto`처럼 단계마다 옮기는 것이 원래 설계 의도입니다.

**❌ Auto Mode면 아무거나 맡겨도 된다고 생각한다**

→ 배포·삭제·전송처럼 되돌리기 어려운 작업은 모드를 낮추세요. 자동 검사는 위험을 줄이지만 없애지는 못합니다.

## 스스로 점검하기

**Q. `default` 모드에서 승인 없이 되는 일은 무엇인가요?**

<details><summary>답 보기</summary>

읽기뿐입니다. 파일 수정·명령 실행·네트워크 요청은 모두 승인을 요구합니다.

</details>

**Q. `auto`와 `bypassPermissions`의 결정적 차이는?**

<details><summary>답 보기</summary>

백그라운드 안전 검사의 유무입니다. `auto`는 검사를 유지하고, `bypassPermissions`는 그것마저 끕니다.

</details>
