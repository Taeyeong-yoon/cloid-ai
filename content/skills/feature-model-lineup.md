**분류 작업에 최상위 모델을 쓰는 건, 편의점 가는 데 트럭을 모는 것과 같습니다.**

## 왜 알아야 하나

모델 선택은 보통 "가장 좋은 것"을 고르는 문제로 오해됩니다. 실제로는 **작업 난이도에 맞추는** 문제입니다.

쉬운 작업에 큰 모델을 쓰면 돈과 시간이 새고, 어려운 작업에 작은 모델을 쓰면 결과를 못 써서 다시 하게 됩니다. 후자가 사실 더 비쌉니다.

## 개념 잡기

| 모델 | 컨텍스트 | 성격 |
|---|---|---|
| **Claude Opus 5** | 1M | 복잡한 에이전트 작업·긴 호흡 코딩 |
| **Claude Sonnet 5** | 1M | 속도와 지능의 균형, 코딩·에이전트에서 Opus에 근접 |
| **Claude Haiku 4.5** | 200K | 가장 빠르고 저렴, 단순 작업용 |

모델 외에 **effort**라는 축이 하나 더 있습니다. 같은 모델에서 사고 깊이를 조절합니다.

| effort | 쓰임 |
|---|---|
| `low` | 짧고 단순한 작업, 지연에 민감할 때 |
| `medium` | 비용 절감이 필요할 때 |
| `high` | 기본값, 대부분의 작업 |
| `xhigh` | 코딩·에이전트 작업 권장 |
| `max` | 정확도가 비용보다 중요할 때 |

## 바로 해보기

1. 자주 하는 작업 3개를 적고 난이도를 상·중·하로 나눕니다.
2. 하 → Haiku, 중 → Sonnet, 상 → Opus로 배정해 봅니다.
3. 같은 작업을 두 모델로 각각 돌려 결과 품질과 응답 시간을 비교합니다.
4. 품질이 같다면 낮은 쪽을 택합니다. 이 한 번의 비교가 이후 비용을 계속 줄여줍니다.

## 흔한 실수

- **❌ 항상 최신·최상위 모델만 쓴다** — 분류·요약·추출 같은 작업은 Haiku로 충분합니다. 비용 대부분이 여기서 샙니다.
- **❌ 비용이 커서 무조건 저렴한 모델로 내린다** — 결과를 못 써서 재작업하면 더 비쌉니다. 모델을 내리기 전에 effort를 먼저 조절해 보세요.
- **❌ 토큰이 많이 나오면 프롬프트를 짧게 쓴다** — 대개 범인은 매 요청에 붙는 고정 맥락(긴 시스템 프롬프트·첨부 문서)입니다. 거기부터 재보세요.

## 스스로 점검하기

**Q1. 모델을 고르는 1차 기준은?**

정답: 작업 난이도입니다. 그다음이 허용 가능한 응답 시간과 비용입니다.

**Q2. 모델을 바꾸지 않고 비용을 줄이는 방법은?**

정답: effort를 낮추고, 반복되는 긴 앞부분을 프롬프트 캐싱으로 재사용합니다.
